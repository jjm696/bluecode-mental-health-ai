# AI 心理健康助手 项目理解与面试说明

## 1. 这个项目是做什么的

这是一个面向心理健康场景的 AI 辅助系统，分成用户端和管理后台两部分。

- 用户端：完成 AI 心理咨询、情绪日记记录、知识库阅读
- 管理后台：查看平台数据、管理知识文章、查看咨询记录、复核情绪风险
- 后端：负责用户、文章、咨询会话、情绪日志和 AI 分析结果的存储与查询

它的核心不是“聊天页面”，而是一个完整的业务闭环：

1. 用户输入情绪或咨询内容
2. 系统保存会话或日志
3. AI 给出分析、标签和建议
4. 后台管理端对数据进行追踪、统计和风险复核

## 2. 简历表述

### 精简版

负责开发 AI 心理健康助手项目，基于 Vue3 + Element Plus 搭建管理后台，设计并实现知识文章、咨询记录、情绪日志、数据分析等核心模块；同时基于 Spring Boot + MyBatis + MySQL 设计后端数据模型，实现用户、咨询会话、情绪分析和知识库内容的结构化管理。

### 强化版

独立完成 AI 心理健康助手项目的前后端核心设计与开发，前端采用 Vue3、Vite、Element Plus 实现后台管理系统，支持知识库筛选、咨询记录查看、情绪日志复核与风险标签展示；后端使用 Spring Boot + MyBatis + MySQL 完成用户、文章、会话、情绪日志、AI 分析等表结构设计，并抽象 controller、service、mapper 分层结构，支撑后续接口联调与业务扩展。

## 4. 面试高频问题

### 这个项目的业务价值是什么？

它解决的是心理健康场景里“记录分散、干预滞后、内容支持弱”的问题。用户端通过 AI 咨询和情绪日记形成数据沉淀，后台端则让管理员能快速查看高风险情绪、活跃会话和知识内容使用情况，从而形成辅助干预闭环。

### 为什么要这样拆表？

因为咨询会话、会话消息、情绪日志、AI 分析结果之间是一对多和一对一混合关系。拆开后，查询、统计和扩展都更清晰，比如会话表保存摘要和风险等级，消息表只保存逐条聊天内容，日志和 AI 分析也分开，便于重复分析和模型替换。

### 为什么选 MySQL？

这个项目后台管理的核心是结构化查询和统计分析，比如筛选文章、按时间统计情绪趋势、按风险等级聚合日志数量、查询用户最近会话，这些都更适合关系型数据库。MySQL 在开发环境搭建、索引支持和后续部署上都比较稳定。

### 数据分析页的数据怎么来？

主要来自对 `emotion_logs`、`consultation_sessions`、`knowledge_articles`、`users` 这些表的聚合查询。比如总用户数直接查 `users`，情绪趋势对 `emotion_logs` 按日期做 `AVG(mood_score)` 和 `COUNT(*)`，风险分布对 `risk_level` 做分组统计。

### 这个项目的难点是什么？

难点不在页面，而在业务抽象。因为它同时有内容管理、咨询记录、情绪分析、风险识别几条业务线，需要先把数据模型设计清楚，否则前端页面和后端接口都会越来越乱。另一个难点是 AI 结果要结构化存储，不能只保存一段文本，所以我把关键词、建议、风险提示、改善建议拆成了独立字段或 JSON 字段。

### 如果继续做，下一步做什么？

- 把前端 mock 数据全部切换为真实接口
- 增加登录鉴权和角色权限控制
- 接入真实 AI 模型生成咨询回复和情绪分析
- 增加分页、上传封面、富文本编辑器和后台操作日志

## 5. 面试时主动强调的点

- 这是一个有明确业务闭环的系统，不是单页 Demo
- 你做了数据结构设计，不只是写页面
- 你考虑了后台管理、风险分级、趋势统计这些真实业务需求
- 你给项目预留了前后端联调和 AI 扩展空间
