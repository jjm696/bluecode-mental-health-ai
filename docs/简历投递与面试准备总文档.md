# AI 心理健康助手：简历投递与面试准备总文档

## 1. 项目定位

这是一个面向用户心理健康陪伴场景的前后端全栈项目，核心功能是让用户通过 AI 咨询、情绪日记和心理知识库进行自助式情绪表达，同时让管理员在后台查看咨询记录、情绪日志和数据概览，形成“用户端记录与咨询 - 后端数据持久化 - 管理端复核分析”的业务闭环。

项目不是单纯的静态页面，也不是只调用 AI API 的 Demo，而是包含用户登录、管理员登录、JWT 鉴权、MySQL 数据建模、DeepSeek API 调用、AI 人设提示词、风险等级判断、前后台数据同步、Railway 云部署和移动端适配的完整系统。

适合放在简历里的项目名称：

```text
AI 心理健康助手系统
```

或更工程化一点：

```text
基于 Spring Boot + Vue3 + MySQL 的 AI 心理健康助手系统
```

## 4. 你必须真正理解的关键点

### 4.1 系统整体架构

你要能画出这个逻辑：

```text
浏览器用户端 / 管理端
        |
        | HTTP 请求，携带 JWT
        v
Spring Boot 后端
        |
        | MyBatis
        v
MySQL 数据库
        |
        | 保存用户、文章、情绪日志、咨询会话、咨询消息

Spring Boot 后端
        |
        | 调用 DeepSeek API
        v
AI 模型返回回复
```

重点表达：

- 前端不直接调用 DeepSeek。
- DeepSeek API Key 不暴露给浏览器。
- AI 调用由后端统一完成。
- 用户消息和 AI 回复都落库。
- 管理端查看的是数据库中的结构化记录。

### 4.2 前端技术点

你需要理解：

- `Vue Router` 如何区分用户端和管理端路由。
- `Pinia` 如何保存用户和管理员状态。
- 为什么使用 `sessionStorage` 而不是 `localStorage`。
- 登录用户和管理员为什么不能在同一标签页同时登录。
- 前端请求如何自动携带 JWT。
- 移动端为什么需要底部导航和输入框字体 16px。

可以这样解释 `sessionStorage`：

```text
我希望同一个浏览器标签页中只保留一种身份，避免用户端和管理端 Token 混用，所以使用 sessionStorage 保存登录态。这样不同标签页可以独立登录，而同一标签页切换身份必须先退出。
```

### 4.3 后端技术点

你需要理解：

- Spring Boot 如何分层：Controller、Service、Mapper、Model。
- MyBatis 如何通过 Mapper 注解执行 SQL。
- JWT 如何生成、解析和校验。
- 拦截器如何拦截需要登录的接口。
- CORS 预检请求为什么要放行 `OPTIONS`。
- MySQL 时区为什么会影响线上显示时间。

关于 CORS 可以这样回答：

```text
线上前端和后端是两个不同域名，浏览器在带 Authorization 请求头时会先发送 OPTIONS 预检请求。如果后端拦截器把 OPTIONS 当成普通业务请求校验 Token，就会返回 401 或 403，浏览器会阻止真正的请求。所以我在 AuthInterceptor 中优先放行 OPTIONS 请求。
```

关于时区可以这样回答：

```text
Railway MySQL 默认可能使用 UTC，会导致 NOW() 和 CURRENT_TIMESTAMP 写入时间比北京时间少 8 小时。我在 JDBC URL 中增加 sessionVariables=time_zone='%2B08:00'，让 MySQL 连接会话按东八区写入时间。
```

### 4.4 AI 模块关键点

这是项目最重要的面试点。

你必须理解：

- DeepSeek 只是通用模型能力。
- 心理助手的人设、语气和边界由项目代码中的 system prompt 控制。
- 后端会把 system prompt、历史消息和用户新消息一起发给模型。
- 高风险内容需要特殊处理，不能只普通安慰。
- AI 回复失败时有本地兜底回复。

可以这样解释：

```text
我没有直接把 DeepSeek 当成普通聊天接口使用，而是在后端服务层构建了心理健康助手的 system prompt。提示词里定义了助手名称、角色定位、回复语气、禁止医疗诊断、对话阶段、场景策略和高风险提醒。模型负责生成自然语言，但产品边界和行为规则由后端控制。
```

### 4.5 数据库设计

你需要理解主要表：

- `users`：普通用户信息。
- `admins`：管理员账号。
- `knowledge_articles`：知识库文章。
- `categories`：文章分类。
- `consultation_sessions`：咨询会话主表。
- `consultation_messages`：每条用户消息和 AI 回复。
- `emotion_logs`：用户情绪日记。
- `emotion_ai_analysis`：情绪分析结果或建议。

咨询模块为什么拆成 session 和 message：

```text
一个咨询会话下会有多轮消息，所以用 consultation_sessions 保存会话摘要、标题、风险等级和主要情绪，用 consultation_messages 保存具体的用户消息和 AI 回复。这样既方便后台按会话分页查看，也能进入详情查看完整对话。
```

### 4.6 部署与安全

你需要理解：

- Railway 上后端和前端是两个服务。
- MySQL 是 Railway 云数据库。
- 前端通过 `VITE_API_BASE_URL` 指向后端公网 API。
- 后端通过环境变量读取数据库连接、JWT 密钥和 DeepSeek Key。
- API Key 不能写进代码，也不能上传 GitHub。

可以这样回答：

```text
我把敏感配置全部放在 Railway 环境变量里，比如 DB_HOST、DB_USERNAME、DB_PASSWORD、JWT_SECRET、DEEPSEEK_API_KEY。代码中的 application.yml 只读取环境变量，不保存真实密钥。
```

## 6. 面试官可能问到的问题与回答

### Q1：这个项目解决了什么问题？

回答：

```text
它面向轻量心理健康陪伴场景，帮助用户通过 AI 对话表达压力和情绪，通过情绪日记记录状态，通过知识库获得心理健康内容支持。后台管理员可以查看咨询记录和情绪日志，方便后续复核和运营分析。
```

### Q2：为什么选择 Spring Boot + MyBatis？

回答：

```text
Spring Boot 适合快速搭建 RESTful 后端服务，生态成熟；MyBatis 对 SQL 控制更直接，适合这个项目中按条件分页查询、会话详情查询、数据统计等场景。我可以明确控制 SQL，也方便理解数据表之间的关系。
```

### Q3：JWT 是怎么做的？

回答：

```text
用户或管理员登录成功后，后端生成 JWT，里面包含 userId 和 role。前端保存 Token，后续请求通过 Authorization: Bearer token 携带。后端 AuthInterceptor 解析 Token，校验登录态和角色权限。
```

### Q4：用户和管理员登录态怎么隔离？

回答：

```text
前端分别维护用户 store 和管理员 store，同一标签页只允许存在一种身份。登录用户会清除管理员状态，登录管理员会清除用户状态。后端也会根据 JWT 中的 role 判断接口权限，避免用户访问管理员接口。
```

### Q5：为什么不用前端直接调用 DeepSeek？

回答：

```text
因为前端直接调用会暴露 API Key，而且无法统一控制用户身份、消息落库、风险判断和提示词策略。所以我把 AI 调用放在后端，前端只调用自己的业务接口。
```

### Q6：AI 心理助手的人设在哪里设置？

回答：

```text
在后端 ConsultationService 的 systemPrompt 方法中设置。这里定义了助手叫“暖光”，定位是心理健康陪伴助手，并约束它先共情、再反映处境、再给一个温和问题或小建议，同时禁止医疗诊断和过度承诺。
```

### Q7：如果用户说“我不想活了”，系统怎么处理？

回答：

```text
后端会通过关键词判断高风险场景，把风险等级提高。system prompt 中也要求模型在高风险表达时优先提醒用户联系现实中的可信任的人，必要时拨打当地紧急电话或前往医院，而不是只做普通安慰。
```

注意：

```text
这个项目不能宣称替代专业心理治疗，只能定位为心理健康辅助和情绪陪伴工具。
```

### Q8：咨询记录是怎么保存的？

回答：

```text
用户发送消息后，后端先创建或找到 consultation_sessions 会话，然后把用户消息写入 consultation_messages。调用 DeepSeek 得到 AI 回复后，再把 AI 回复也写入 consultation_messages，并更新会话的摘要、主要情绪、风险等级、消息数量和更新时间。
```

### Q9：为什么要有管理端？

回答：

```text
管理端让这个项目从单纯用户工具变成完整业务系统。用户端负责产生咨询和情绪数据，管理端负责查看、筛选和复核数据，例如查看高风险咨询、情绪日志和文章内容管理。
```

### Q10：你遇到过什么线上问题？

可以说这几个：

```text
1. JWT 密钥长度不足导致登录报错，后来改成符合 HS256 要求的安全密钥。
2. 跨域预检 OPTIONS 被鉴权拦截，导致线上前端 Failed to fetch，后来在拦截器中放行 OPTIONS。
3. Railway MySQL 使用 UTC 导致时间显示差 8 小时，后来在 JDBC URL 中设置 MySQL 会话时区。
4. 手机浏览器点击输入框自动放大页面，后来把移动端输入框字体统一设置为 16px，并在提交时主动 blur 输入框。
```

### Q11：轮询和 WebSocket 为什么选择轮询？

回答：

```text
这个项目当前主要是简历项目和轻量后台管理场景，对实时性要求不是毫秒级，所以使用定时轮询实现近实时同步，复杂度更低，也更容易部署和维护。如果后续要做多人在线咨询或管理员实时预警，可以再升级成 WebSocket。
```

### Q12：如果 AI API 调用失败怎么办？

回答：

```text
后端 AiChatService 中有 fallbackReply。如果 DeepSeek API Key 缺失、接口异常或响应格式不符合预期，会返回本地兜底回复，保证用户不会看到系统崩溃。
```

### Q13：项目有哪些不足？

回答要诚实，但要有改进方向：

```text
目前项目更偏简历级完整系统，风险识别主要基于关键词和提示词策略，还没有接入专业心理风险评估模型；实时同步使用轮询而不是 WebSocket；后台统计维度还可以继续扩展。后续可以加入更细的风险规则、消息审核、WebSocket 实时提醒和更完整的数据可视化。
```

### Q14：你在项目中最有技术含量的部分是什么？

回答：

```text
我认为是 AI 咨询模块的后端设计。它不是简单把用户输入转发给 DeepSeek，而是做了会话管理、消息持久化、历史上下文拼接、心理助手 system prompt、场景识别、风险等级判断、AI 回复落库和后台复核字段更新。这个模块同时涉及业务建模、AI 调用、数据一致性和安全边界。
```

## 8. 你复习时的重点顺序

优先级从高到低：

1. 能完整讲清楚系统架构和业务流程。
2. 能讲清楚 AI 咨询从前端发送到后端落库再到 DeepSeek 回复的完整链路。
3. 能讲清楚 JWT 登录、角色隔离和拦截器。
4. 能讲清楚 MySQL 表设计，尤其是咨询会话和消息表为什么拆开。
5. 能讲清楚 DeepSeek 只是模型能力，人设和边界由后端 prompt 控制。
6. 能讲清楚线上部署时遇到的 CORS、时区、环境变量、移动端输入缩放问题。
7. 能诚实说明项目不足和下一步优化方向。

## 9. 面试中不要踩的坑

不要说：

```text
这个系统可以治疗心理疾病。
```

应该说：

```text
这个系统定位为心理健康辅助和情绪陪伴，不替代专业心理咨询或医疗诊断。
```

不要说：

```text
AI 的回答完全由 DeepSeek 决定。
```

应该说：

```text
模型负责语言生成，但助手的人设、语气、风险边界和回复策略由后端 system prompt 和业务规则控制。
```

不要说：

```text
我只是调了一个 API。
```

应该说：

```text
我围绕 AI 咨询做了会话建模、消息持久化、上下文拼接、提示词策略、风险识别和后台复核闭环。
```

不要夸大：

```text
系统能准确识别所有心理风险。
```

应该说：

```text
当前风险识别是基于关键词和模型提示词的轻量策略，适合简历项目展示，后续可以接入更专业的风险评估规则或人工复核流程。
```

## 10. 推荐你最终掌握的一句话

```text
这个项目的核心价值不是“调用了 AI”，而是我把 AI 能力放进了一个完整的心理健康辅助业务系统里：前端负责用户体验，后端负责鉴权、数据持久化和 AI 策略控制，MySQL 负责沉淀咨询和情绪数据，管理端负责查看和复核，从而形成一个可上线访问的前后端闭环项目。
```
